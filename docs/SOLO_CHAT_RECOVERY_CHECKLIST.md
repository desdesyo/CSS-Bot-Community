# SOLO.Chat — обязательный чек-лист восстановления

Этот чек-лист является обязательным критерием приёмки любого исправления, восстановления или релиза SOLO.Chat.

## Правило допуска

Статус `RECOVERED` / «ВОССТАНОВЛЕН» запрещён, пока все четыре проверки не завершены успешно на работающем экземпляре приложения. Успешная сборка, прохождение unit-тестов, запуск процесса или HTTP 200 на главной странице не заменяют сквозную проверку диалога.

Каждый прогон должен сохранять дату/время, commit SHA, URL/окружение, идентификатор тестового прогона, результаты шагов и ссылки на логи/артефакты. Секреты, токены и содержимое приватных пользовательских сообщений в артефакты не записывать.

## Обязательные проверки

- [ ] **1. Чат открывается.** Открыть реальную страницу приложения. Проверить, что интерфейс отрисован и интерактивен, нет пустого экрана, бесконечной загрузки или фатальных ошибок клиента. Доказательство: URL окружения, результат проверки готовности UI, ошибки консоли.
- [ ] **2. Сообщения отправляются.** Ввести уникальный тестовый текст и отправить его штатным способом. Убедиться, что сообщение появляется в диалоге и запрос действительно принят сервером; одного локального отображения недостаточно. Доказательство: request ID, HTTP/transport result и запись серверного приёма.
- [ ] **3. SOLO.Chat обрабатывает запрос.** Проследить тот же request ID через backend, маршрутизацию/оркестратор и выбранный обработчик/агента. Убедиться, что обработка завершилась, а не зависла, не была молча отброшена и не завершилась только заглушкой. Доказательство: коррелированные серверные события со статусом завершения.
- [ ] **4. Пользователь получает ответ.** Убедиться, что ответ для того же request ID возвращён клиенту и виден в исходном диалоге. Проверить непустой ответ и отсутствие ошибки/вечного индикатора ожидания. Доказательство: response event/payload (без секретов) и подтверждение отображения в UI.

## Итоговый статус

- **PASS:** все 4 пункта отмечены, доказательства приложены, request ID совпадает на всём пути от отправки до отображения ответа.
- **FAIL:** любой пункт не пройден, отсутствует доказательство или цепочка корреляции нарушена.
- **BLOCKED:** тест невозможно выполнить из-за недоступного окружения/секрета/зависимости. BLOCKED не считается восстановлением.

## Обязательное поведение восстановления

1. После каждого исправления запускать весь чек-лист заново, а не только тест затронутого компонента.
2. При FAIL определить первый сломанный этап цепочки, приложить логи и передать дефект ответственному агенту.
3. После исправления повторить все четыре проверки с новым уникальным тестовым сообщением.
4. Оркестратор/релизный процесс не должен объявлять восстановление успешным, пока нет PASS 4/4.
5. Если реальный UI/backend недоступен тестовому раннеру, результат помечается BLOCKED; нельзя подменять сквозной тест моками и выдавать его за доказательство работы в production.

## Минимальный формат отчёта

```text
SOLO_CHAT_RECOVERY: PASS | FAIL | BLOCKED
commit: <sha>
environment: <url/name>
run_id: <unique-id>
1_chat_opens: PASS|FAIL + evidence
2_message_sends: PASS|FAIL + request_id/evidence
3_request_processed: PASS|FAIL + request_id/evidence
4_reply_displayed: PASS|FAIL + request_id/evidence
first_failed_stage: <1..4 or none>
logs_artifacts: <links>
```
