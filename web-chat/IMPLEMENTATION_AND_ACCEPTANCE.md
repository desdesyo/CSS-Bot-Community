# План реализации, исправления и приёмки AI Chat

**Цель:** довести GitHub Chat до реально работающего, локализованного русскоязычного AI-сервиса. Не считать публикацию Worker или успешную сборку доказательством работоспособности чата.

## Обязательные правила выполнения

- Работать самостоятельно по репозиторию и доступным инструментам: изучать код, вносить изменения, запускать проверки, анализировать логи, устранять причины ошибок и повторять тесты.
- Не просить пользователя выполнять технические действия, которые агент способен выполнить сам. Если необходим недоступный секрет, разрешение, платная функция или действие в чужом аккаунте — назвать конкретный блокер и не изображать его решённым.
- Не выдавать предположение за результат. Для каждого этапа сохранять проверяемые доказательства: commit, CI run, HTTP-ответ, лог, тестовый результат или артефакт.
- Не скрывать ошибки и не подменять их общими сообщениями «временно недоступно». Пользовательский интерфейс должен показывать безопасное, но диагностически полезное сообщение; подробности — в серверном журнале без утечки секретов.
- Перед изменением изучить текущую архитектуру, зависимости, конфигурацию, существующие тесты и документацию. Сохранить рабочие функции, если они не конфликтуют с безопасностью или корректностью.

## Этапы реализации

### 1. Самостоятельная разработка / доработка настоящего AI-чата

- Проверить frontend, Worker, Durable Object, модельный провайдер, хранение диалогов, авторизацию, GitHub API и deployment workflow.
- Реализовать полноценный путь: UI → API → авторизация → модель/агент → сохранение ответа → отображение ответа.
- Проверить конфигурацию всех обязательных переменных и bindings. Устранить несоответствия между Dashboard и Wrangler, насколько это доступно через репозиторий и API.
- Обеспечить сохранение истории, создание нового диалога, открытие старого, контекст предыдущих сообщений, обработку длинных запросов и ошибок.
- Не оставлять фиктивные кнопки и функции, которые выглядят рабочими, но не подключены. Не заявлять о sandbox, инструментах или возможностях, которых фактически нет.

### 2. Самостоятельное устранение ошибок

- Проверить TypeScript, lint (если настроен), unit/integration-тесты, сборку и CI.
- Исправлять первопричину, а не маскировать симптомы.
- После каждого исправления повторять соответствующий тест и регрессионные проверки.
- Проверять HTTP-коды, таймауты, повторные запросы, некорректные JSON, пустые ответы модели, ошибки GitHub API, ограничения модели и Durable Object.
- Убедиться, что при сбое пользовательское сообщение не теряется и не дублируется при retry.

### 3. Самостоятельная авторизация и первая тестовая переписка

- Открыть опубликованный сервис и пройти реальный путь авторизации, используя только доступные агенту средства и законно доступные credentials.
- Проверить валидный и неверный пароль, сохранение сессии и logout/повторный вход.
- Отправить тестовое сообщение, получить ответ модели, проверить отображение и запись обоих сообщений в историю.
- Открыть этот диалог заново и подтвердить, что история восстановлена.
- Если агент не имеет браузерного/сетевого доступа или необходимых credentials, зафиксировать это как блокер; не писать, что авторизация или переписка протестированы.

### 4. Задание чату создать утилиту после успешной переписки

- Только после успешного этапа 3 дать самому развернутому чату отдельную задачу: **создать небольшую полезную утилиту**, например валидатор JSON с CLI и тестами.
- Задача должна требовать реального артефакта в рабочем GitHub-репозитории: исходный код, README, тесты и понятный commit/PR.
- Проверить, что чат не просто описал решение, а фактически использовал инструменты и создал файлы/commit.
- Сохранить ссылку на созданный артефакт и лог выполнения.

### 5. Контроль исполнения и повторная настройка

- Проверить каждый критерий задачи утилиты: файлы существуют, код соответствует назначению, README содержит запуск, тесты присутствуют и проходят.
- Если чат не выполнил задачу, выполнил её частично или сообщил ложный результат:
  1. воспроизвести ошибку;
  2. найти причину в коде, промпте, инструментах, разрешениях, модели или конфигурации;
  3. внести исправление;
  4. повторить тестирование самого чата;
  5. повторно поручить ему ту же задачу в чистом тестовом диалоге.
- Не засчитывать ручное создание утилиты разработчиком как доказательство того, что чат умеет создавать её самостоятельно.

### 6. Повторное задание и подтверждение исправлений

- После перенастройки выдать чату новую, независимую задачу того же уровня сложности.
- Проверить полный цикл: постановка → план → вызовы инструментов → создание/изменение файлов → тесты → commit → отчёт со ссылками.
- Подтвердить, что ошибки первого прогона не повторились.
- Проверить, что чат не заявляет о запуске тестов, изменении файлов или commit без реальных подтверждений.

### 7. Полная проверка работоспособности и способностей

Провести и записать результаты минимум следующих тестов:

- обычный вопрос и связный ответ;
- уточняющий вопрос с учётом предыдущего контекста;
- новый диалог и восстановление старого;
- длинное сообщение, пустое сообщение, превышение лимита;
- ошибка/таймаут модели и корректное восстановление;
- работа GitHub-инструментов: чтение, создание и изменение файла, проверка commit;
- задача на анализ исходного кода и задача на исправление ошибки;
- проверка отказа при отсутствии прав/невалидных credentials;
- проверка отсутствия утечки токенов, пароля и приватных данных в UI, логах и репозитории;
- повторное выполнение одного запроса без случайного дублирования операций;
- проверка доступности сервиса после deployment и отсутствие регрессий.

Для каждого теста указать: шаги, ожидаемый результат, фактический результат, статус PASS/FAIL, ссылку на лог/commit/CI. Не ставить PASS без доказательства.

### 8. Локализация

- Полностью локализовать интерфейс, сообщения об ошибках, статусы, кнопки, подсказки и onboarding на **русский язык**.
- Установить русский язык общения по умолчанию для AI-ассистента; сохранять язык пользователя, если он явно выбрал другой.
- Перевести документацию пользователя и инструкции по настройке на русский.
- Проверить корректность UTF-8, кириллицы, мобильной верстки, дат/времени и доступных сообщений об ошибках.
- Не переводить названия API, ключи конфигурации, команды CLI и идентификаторы, которые должны оставаться точными.

## Итоговый критерий готовности

Чат считается готовым только если:

1. Авторизация реально пройдена.
2. Первая переписка успешно отправлена, ответ получен и сохранён.
3. Чат самостоятельно создал утилиту через свои инструменты.
4. Утилита проверена по содержимому и тестам.
5. После исправлений чат успешно выполнил повторную независимую задачу.
6. Все обязательные проверки этапа 7 имеют PASS либо явно перечислены оставшиеся блокеры.
7. Интерфейс и пользовательские сообщения локализованы на русский.
8. Есть итоговый отчёт с commit SHA, URL deployment, ссылками на CI, тестовыми доказательствами, созданной утилитой и перечнем ограничений.

**Запрещено:** объявлять чат «готовым» по одному успешному deploy, одному зелёному CI или наличию страницы входа. Готовность подтверждается только end-to-end проверками реальной переписки и выполнения инструментальной задачи.
